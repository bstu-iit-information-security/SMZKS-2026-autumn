**Теоретическая база**

Протокол HTTP является stateless (не сохраняющим состояние) протоколом: каждый запрос клиента к серверу обрабатывается изолированно. Для идентификации пользователя между запросами используются файлы Cookies (куки) — небольшие фрагменты данных, которые сервер передает клиенту через заголовок Set-Cookie, а клиент автоматически возвращает в последующих запросах через заголовок Cookie.

Атрибуты безопасности Cookies:

* _HttpOnly:_ запрещает доступ к cookies со стороны клиентских скриптов (JavaScript через document.cookie), что является базовой защитой от кражи сессий при XSS-атаках.

* _Secure:_ гарантирует передачу cookies исключительно по зашифрованному протоколу HTTPS.

* _SameSite:_ защищает от межсайтовой подделки запросов (CSRF), контролируя отправку cookies при кросс-доменных запросах.

Рассматриваемые уязвимости:

1. _Инъекции кода баз данных (SQL Injection / SQLi)._
SQL-инъекция возникает в случаях, когда входные данные пользователя не проходят процедуру фильтрации, санитизации или параметризации, а напрямую конкатенируются (склеиваются) со строкой SQL-запроса, выполняемого интерпретатором базы данных. Злоумышленник может внедрить управляющие конструкции SQL-языка (например, логические операторы OR), изменив логику выполнения запроса.
Безопасный код рассматривает пользовательский ввод как данные (литералы), обрабатывая их отдельно от команд управления базой данных. Уязвимый код использует конкатенацию (склеивание строк), из-за чего интерпретатор СУБД не может отличить легитимные учетные данные от управляющих символов SQL (кавычек ', операторов OR, комментариев --). Внедрение логического условия OR 1=1 принудительно делает предикат WHERE истинным для любой строки в таблице, обходя проверку подлинности.

2. _Межсайтовый скриптинг (Cross-Site Scripting / XSS)._
Reflected (отраженный) XSS возникает, когда приложение принимает пользовательский ввод из параметров запроса (например, из строки поиска) и сразу возвращает его в теле HTTP-ответа без экранирования специальных символов (<, >, "). В результате браузер жертвы интерпретирует входящий текст как исполняемый код на языке JavaScript, выполняя его в контексте доверенной сессии пользователя. 
Уязвимость XSS возникает из-за отсутствия контекстно-зависимого экранирования (Context-Aware Output Encoding). Когда сервер возвращает пользовательский ввод в HTML-документ, специальные символы (<, >, &, ") должны быть заменены на безопасные HTML-сущности (&lt;, &gt;). Если этого не происходит, браузер жертвы переключается из режима интерпретации текста в режим интерпретации разметки, выполняя переданный сценарий (например, тег \<script>) в том же сессионном контексте. Политика CSP решает эту проблему принципиально иначе: она запрещает исполнение встроенных (inline) скриптов на уровне политик безопасности браузера, игнорируя наличие тегов в тексте.

3. _Нарушение авторизации на уровне объектов (BOLA / IDOR)._
BOLA (Broken Object Level Authorization) — уязвимость контроля доступа, возникающая при обращении к ресурсам по прямому идентификатору (например, /api/profile/1). Если бэкенд-приложение не выполняет проверку прав текущего сеанса пользователя на просмотр запрашиваемого идентификатора, злоумышленник может получить доступ к конфиденциальным данным других пользователей путем перебора ID.

JSON Web Token (JWT) — это открытый стандарт (RFC 7519) для безопасной передачи утверждений между сторонами. Токен состоит из трех частей, разделенных точками:

* _Header (Заголовок)_: указывает тип токена и алгоритм подписи (например, HS256).

* _Payload (Полезная нагрузка)_: содержит утверждения (claims) — user_id, username, role, время истечения срока (exp).

* _Signature (Подпись)_: формируется путем хеширования заголовка и полезной нагрузки с использованием секретного ключа (JWT_SECRET).
Если секретный ключ является слабым (например, коротким словом), его можно восстановить методом перебора по словарю (Brute-force), после чего злоумышленник может самостоятельно сформировать произвольный токен с измененными привилегиями (например, изменив role на admin).
Токен JWT базируется на концепции криптографической целостности, а не конфиденциальности (полезная нагрузка Payload кодируется в Base64, но не шифруется — её может прочитать любой). Безопасность токена держится исключительно на цифровой подписи (Signature), которая вычисляется по алгоритму $HMAC(Header \cdot Payload, Secret)$. Если секретный ключ является коротким словом из словаря, стойкость алгоритма сводится к нулю: злоумышленник может перебрать все варианты ключа за секунды, вычислить HMAC для измененного Payload (повысив права до admin) и выдать поддельный токен за легитимный.

Политика защиты контента (Content Security Policy / CSP) – это механизм безопасности в виде HTTP-заголовка, позволяющий владельцу веб-ресурса ограничить домены, с которых браузер имеет право загружать и выполнять скрипты, изображения и другие ресурсы, нейтрализуя атаки класса XSS.
