## Лабораторная работа №4. Сбор, нормализация и корреляция событий информационной безопасности в системах централизованного мониторинга

**Цель работы:** практическое освоение развертывания SIEM на базе Wazuh 4.7.3, настройки агента сбора журналов (веб-сервер Nginx и системный журнал Linux) и написания пользовательских правил корреляции для выявления веб-атак.

**Что нужно заранее:** Docker с Compose v2, Git, терминал Linux (на Windows – Ubuntu в WSL 2), не менее 6 ГБ памяти, выделенной Docker, и около 10 ГБ свободного места на диске.

### Шаг 1. Подготовка рабочей среды

#### 1.1. Windows: работа в WSL 2

Все команды лабораторной выполняются в терминале Ubuntu, а не в PowerShell. Исключение явно указано в тексте.
1. Если Ubuntu не установлена, откройте PowerShell и выполните `wsl --install -d Ubuntu`. После перезагрузки задайте имя пользователя и пароль.
2. В Docker Desktop откройте *Settings → Resources → WSL Integration* и включите интеграцию для Ubuntu.
3. Установите Git в Ubuntu:
   ```
   sudo apt-get update && sudo apt-get install -y git
   ```

Работайте только в домашней папке Ubuntu (`~`), а не в папках дисков Windows (`/mnt/c`, `/mnt/e`). Генератор сертификатов меняет владельца и права файлов, а при монтировании дисков Windows Docker Desktop такие изменения часто не выполняет. В этом случае генерация сертификатов завершается ошибкой `Permission denied`.

#### 1.2. Linux и macOS

Работайте в обычном терминале в домашней папке.

#### 1.3. Лимит виртуальной памяти

Индексер не запустится, пока на хосте не увеличен параметр `vm.max_map_count`:
* Linux: `sudo sysctl -w vm.max_map_count=262144`;
* Windows: в **PowerShell** (не в Ubuntu) выполните `wsl -d docker-desktop -e sysctl -w vm.max_map_count=262144`. Значение сбрасывается при перезапуске Docker Desktop, команду нужно повторить;
* macOS: дополнительных действий обычно не требуется, проверьте значение командой из пункта 1.4. Если оно меньше, сообщите преподавателю.

#### 1.4. Проверка (любая ОС):
```
docker run --rm alpine cat /proc/sys/vm/max_map_count
```
Команда должна вывести `262144` или большее число.

### Шаг 2. Развертывание стенда

#### 2.1. Официальный стенд Wazuh

В работе используется официальный репозиторий `wazuh-docker` версии 4.7.3. Его файлы не меняйте: в них уже настроены сертификаты, пользователи и роли индексера. К стенду добавляется только целевой сервер с агентом.

```
cd ~
git clone -b v4.7.3 https://github.com/wazuh/wazuh-docker.git wazuh-lab
cd wazuh-lab/single-node
```

#### 2.2. Добавление целевого сервера

Преподаватель выдает папку `agent/` и файл `docker-compose.override.yml`. Скопируйте их в папку `~/wazuh-lab/single-node/`:
* в Windows откройте в проводнике путь `\\wsl$\Ubuntu\home\<имя_пользователя>\wazuh-lab\single-node` и поместите файлы туда;
* в Linux и macOS скопируйте файлы обычным способом.

Итоговая структура папки:
```
single-node/
├── docker-compose.yml            (официальный, не меняется)
├── docker-compose.override.yml   (добавлен в лабораторной)
├── generate-indexer-certs.yml    (официальный)
├── config/                       (официальный)
└── agent/
    └── Dockerfile                (добавлен в лабораторной)
```
Файл `docker-compose.override.yml` Docker Compose применяет автоматически вместе с `docker-compose.yml`.

#### 2.3. Генерация сертификатов (выполняется один раз):
```
docker compose -f generate-indexer-certs.yml run --rm generator
ls config/wazuh_indexer_ssl_certs
```
В папке должны появиться файлы `root-ca.pem`, `admin.pem`, `admin-key.pem`, `wazuh.indexer.pem`, `wazuh.indexer-key.pem`, `wazuh.manager.pem`, `wazuh.manager-key.pem`, `wazuh.dashboard.pem`, `wazuh.dashboard-key.pem`. Если появилась ошибка `Permission denied`, вы работаете не в домашней папке WSL (см. пункт 1.1).

#### 2.4. Запуск стенда:
```
docker compose up -d --build
docker compose ps
```
Первый запуск занимает несколько минут: собирается образ агента и запускаются компоненты. В `docker compose ps` все четыре сервиса (`wazuh.indexer`, `wazuh.manager`, `wazuh.dashboard`, `target-agent`) должны быть в статусе `running`.

#### 2.5. Контрольные точки

Переходите к заданиям, только когда пройдены все четыре проверки.

1. Индексер отвечает и принимает пароль. Порт 9200 публикуется на хост: в `docker compose ps` видно `0.0.0.0:9200->9200/tcp`. Проверка в Ubuntu:
   ```
   curl -k -u admin:SecretPassword https://127.0.0.1:9200
   ```
   В ответе JSON с полями `cluster_name` и `version`. Если порт не отвечает, а `docker compose ps` не показывает `0.0.0.0:9200`, значит публикация не удалась: пересоздайте контейнер (`docker compose up -d`). В качестве запасной проверки можно выполнить команду изнутри сети стенда: `docker compose exec target-agent curl -k -u admin:SecretPassword https://wazuh.indexer:9200`. Если вместо ответа появилось сообщение `OpenSearch Security not initialized`, см. пункт 2.7.
2. Менеджер подключен к индексеру:
   ```
   docker compose exec wazuh.manager filebeat test output
   ```
   В выводе есть строка `talk to server... OK`.
3. Агент видит менеджер по имени:
   ```
   docker compose exec target-agent getent hosts wazuh.manager
   ```
   В выводе есть IP-адрес.
4. Веб-интерфейс и целевой сервер. Откройте в браузере `https://127.0.0.1`, примите предупреждение о самоподписанном сертификате и войдите как `admin` / `SecretPassword`. Затем выполните `curl http://127.0.0.1:8080`: должна вернуться страница с текстом «Welcome to nginx».

Логин `admin`, пароль `SecretPassword` задаются в официальном `docker-compose.yml`. Менять их в этой работе не нужно.

Если контрольная точка не пройдена:
* Имена `wazuh.indexer` и `wazuh.manager` не резолвятся: в `filebeat test output` ошибка `DNS lookup failure`, `getent hosts` ничего не выводит, а `curl` из `target-agent` пишет `Could not resolve host`. Индексер при этом может работать. Причина в сети Docker Desktop, а не в конфигурации стенда. Сделайте по порядку:
  1. Отключите VPN на время работы: он часто ломает DNS контейнеров.
  2. В PowerShell выполните `wsl --shutdown`, затем снова откройте Docker Desktop и дождитесь зеленого статуса.
  3. Повторите команду из пункта 1.3 (`wsl -d docker-desktop -e sysctl -w vm.max_map_count=262144`). После перезапуска Docker Desktop этот параметр сбрасывается, и без него индексер не запустится.
  4. В Ubuntu выполните `cd ~/wazuh-lab/single-node`, затем `docker compose down` и `docker compose up -d`. Без `-v` данные индексера и сертификаты сохраняются, заново инициализировать безопасность не нужно.
  5. Если имена по-прежнему не резолвятся, выполните `docker run --rm alpine nslookup docker.com` и `docker run --rm alpine ping -c 2 8.8.8.8`. Передайте преподавателю вывод обеих команд.
* Индексер в статусе `restarting`, в логах `max virtual memory areas`: повторите пункт 1.3 и выполните `docker compose restart wazuh.indexer`.
* Индексер завершается с `OutOfMemoryError`: увеличьте память Docker до 6 ГБ и более.
* `OpenSearch Security not initialized`: проверьте, что папка `config/wazuh_indexer/` на месте и содержит файл `internal_users.yml`. Затем выполните `docker compose down -v`, `docker compose up -d --build` и повторите проверку 1. Если не помогло, сообщите преподавателю и приложите вывод `docker compose logs wazuh.indexer | tail -50`.
* Агент не появляется в разделе Agents: посмотрите журнал `docker compose logs target-agent | tail -50` и сравните версии. Версии агента и менеджера должны совпадать (4.7.3):
  ```
  docker compose exec target-agent /var/ossec/bin/wazuh-control info
  docker compose exec wazuh.manager /var/ossec/bin/wazuh-control info
  ```

#### 2.6. Управление стендом:
* остановить и запустить без потери настроек: `docker compose stop`, затем `docker compose start`;
* перезапустить один сервис: `docker compose restart wazuh.manager`;
* посмотреть журнал сервиса: `docker compose logs -f wazuh.manager` (вместо `wazuh.manager` можно указать `wazuh.indexer`, `wazuh.dashboard` или `target-agent`);
* полный сброс данных, агентов и правил: `docker compose down -v`, затем `docker compose up -d --build`.

**Внимание:** команда `docker compose down` без `-v` удаляет контейнеры, а вместе с ними и изменения в конфигурации агента. Между занятиями используйте `stop` и `start`.

**Задание 2. Написание пользовательских правил корреляции**

1. В Dashboard откройте *Management → Rules → Manage rule files* и выберите файл `local_rules.xml`. Названия пунктов меню могут немного отличаться в зависимости от версии интерфейса.
2. Каждое правило обязательно должно находиться внутри элемента `<group>`. Шаблон структуры:
   ```xml
   <group name="local,web,attack,">
     <rule id="ID_ИЗ_ВАРИАНТА" level="УРОВЕНЬ_ИЗ_ВАРИАНТА">
       <if_sid>31100</if_sid>
       <match>СИГНАТУРА_ИЗ_ВАРИАНТА</match>
       <description>Краткое описание атаки</description>
       <mitre>
         <id>ТЕХНИКА_MITRE_ИЗ_ВАРИАНТА</id>
       </mitre>
     </rule>
   </group>
   ```
   Подставьте значения из вашего варианта. Сигнатуру берите из таблицы вариантов в закодированном виде (см. задание 3).
3. Если в файле уже есть пример правила с таким же ID, замените его. Повторяющийся ID не даст менеджеру загрузить правила.
4. Сохраните файл и перезапустите менеджер:
   ```
   docker compose restart wazuh.manager
   docker compose exec wazuh.manager tail -n 50 /var/ossec/logs/ossec.log
   ```
   В журнале не должно быть ошибок, связанных с правилами.
5. Проверьте правило через `wazuh-logtest` (обязательно для каждого варианта). Отправьте запрос своего варианта из задания 3 (пункт 2), затем скопируйте последнюю строку журнала агента:
   ```
   docker compose exec target-agent tail -n 1 /var/log/nginx/access.log
   ```
   и вставьте ее в утилиту проверки правил:
   ```
   docker compose exec wazuh.manager /var/ossec/bin/wazuh-logtest
   ```
   В выводе должна появиться фаза `Completed filtering (rules)` с ID вашего правила. Если правила нет, сначала проверьте, что строка из `access.log` содержит сигнатуру дословно. Для варианта 8 это особенно важно: в сигнатуре есть символы `$` и `*`.

**Задание 3. Симуляция атак и аудит инцидентов**

1. Сигнатуры в таблице вариантов записаны в том виде, в котором они попадают в `access.log`. Поэтому спецсимволы в запросе нужно передавать в закодированном виде:

   | Символ | Как передать в URL |
   |:-------|:-------------------|
   | пробел | `%20` |
   | `<` / `>` | `%3C` / `%3E` |
   | `"` | `%22` |
   | `;` | `%3B` |
   | `{` / `}` | `%7B` / `%7D` |

   Важно: `<match>` сравнивает правило с полной строкой лога. Если кодировка в запросе и в правиле не совпадает, правило не сработает.

2. Используйте `curl` с двумя флагами:
   * `--path-as-is`: curl по умолчанию удаляет из пути последовательности `../`, и без этого флага атака обхода каталога не дойдет до сервера в исходном виде;
   * `-g`: отключает разбор фигурных скобок `{}` как шаблонов curl.

   Шаблон команды: `curl -g --path-as-is 'http://127.0.0.1:8080<ПУТЬ>'`.

   Используйте одинарные кавычки, а не двойные: в интерактивном bash символ `!` внутри двойных кавычек запускает history expansion, и запрос варианта 7 не отправится.

   Подставьте в `<ПУТЬ>` запрос своего варианта. Сигнатура из таблицы вариантов должна входить в строку запроса дословно, в закодированном виде:

   | Вариант | `<ПУТЬ>` |
   |:--|:--|
   | 1 | `/?id=1%20UNION%20SELECT%201` |
   | 2 | `/?q=%3Cscript%3Ealert(1)%3C/script%3E` |
   | 3 | `/../../../etc/passwd` (нужен флаг `--path-as-is`) |
   | 4 | `/?cmd=1%3B%20cat%20/etc/shadow` |
   | 5 | `/?page=php://filter/convert.base64-encode/resource=index` |
   | 6 | `/?x=eval(base64_decode(1))` |
   | 7 | `/?xml=%3C!ENTITY%20xxe%20SYSTEM%20%22file:///etc/passwd%22%3E` |
   | 8 | `/?t=$%7B7*7%7D` |
   | 9 | `/..%2f..%2fetc%2fpasswd` |
   | 10 | `/cmd.php?c=whoami` |
   | 11 | `/?q=1%20WAITFOR%20DELAY%200:0:5` |
   | 12 | `/?x=%3Cimg%20src=x%20onerror=alert(1)%3E` |
   | 13 | `/?data=O:8:%22stdClass%22:0:%7B%7D` |
   | 14 | `/?url=http://169.254.169.254/latest/meta-data/` |
   | 15 | `/?cmd=whoami%3B%20id` |

   Пример можно заменить любым другим запросом, если сигнатура остается в нем без изменений.

3. Убедитесь, что строка попала в журнал:
   ```
   docker compose exec target-agent tail -n 1 /var/log/nginx/access.log
   ```
   Сигнатура из вашего варианта должна быть видна в строке в том же виде, что и в правиле.

4. Откройте *Security events* в Dashboard. Алерт появляется через 10–30 секунд. Встроенные правила Wazuh могут сработать на ту же строку. В отчет берите именно алерт с ID вашего правила.

5. Найдите алерт и проверьте: инцидент имеет заданный Level, правильно определен ID правила, в деталях виден сработавший `match`, корректно отображаются метаданные атаки (IP-адрес злоумышленника, целевой URI, ID техники MITRE ATT&CK). IP-адрес в алерте будет адресом шлюза Docker-сети (обычно `172.x.0.1`), а не `127.0.0.1`: запрос идет через проброс портов с хоста. Это нормально, в отчете укажите именно этот адрес.
6. Если алерта нет, проверьте по порядку:
   * строки нет в `access.log`: запрос не дошел до сервера, проверьте адрес, порт и кодировку;
   * `wazuh-logtest` не показывает правило: проблема в сигнатуре или кодировке запроса;
   * `wazuh-logtest` показывает правило, но алерта нет: посмотрите *Security events* за последние минуты и журнал менеджера `docker compose exec wazuh.manager tail -n 50 /var/ossec/logs/ossec.log`.

### Теоретическая база

Система управления информацией и событиями безопасности (SIEM) – это программный комплекс, обеспечивающий централизованный сбор, агрегацию, анализ и хранение журналов событий (логов) с серверов, сетевого оборудования и средств защиты информации. Главная задача SIEM – корреляция, то есть установление связей между разрозненными событиями для выявления сложных атак и инцидентов.

Платформа Wazuh состоит из трех ключевых компонентов:

1. **Wazuh Agent** устанавливается на конечные узлы (хосты). Он собирает системные логи, проверяет целостность файлов (FIM) и передает данные на сервер.
2. **Wazuh Server** – ядро системы. Оно принимает данные от агентов, пропускает их через декодеры (извлекают поля: IP-адрес, URL, код ответа) и применяет правила для выявления атак и аномалий.
3. **Wazuh Indexer и Dashboard:** подсистема хранения (индексирования, на базе OpenSearch) и визуализации данных. Ранее аналогичную роль выполнял стек ELK (Elasticsearch, Logstash, Kibana).

Правила в Wazuh описываются в формате XML и хранятся в файле `local_rules.xml` (пользовательские правила менеджера). Основные элементы правила:

* `<group name="...">` – обязательная обертка: каждое правило должно принадлежать хотя бы одной группе.
* `id` – уникальный номер правила. Пользовательские правила нумеруются, как правило, начиная со 100000.
* `level` – уровень критичности от 0 до 15. Уровень влияет на важность события. По умолчанию в журнал алертов попадают события от уровня 3.
* `if_sid` – ID родительского правила. Правило 31100 – базовое правило Wazuh для записей access-лога веб-сервера (группа `web,accesslog`), поэтому пользовательские правила для веб-атак обычно наследуются от него.
* `match` / `pcre2` – строка или регулярное выражение, которое ищется в строке лога. Строка лога, как правило, содержит URL в закодированном виде.
* `mitre` – привязка к базе тактик и техник злоумышленников MITRE ATT&CK. Записывается в виде `<mitre><id>T1190</id></mitre>`.

### Отчет по лабораторной работе

Отчет выполняется каждым студентом индивидуально в бумажном виде и сдается преподавателю на практическом занятии. Номер индивидуального варианта отражается на титульном листе. Все задания выполняются строго по своему варианту.

Оформление отчета должно соответствовать общим требованиям к текстовым учебным документам (шрифт Times New Roman, 14 pt, межстрочный интервал 1.5, выравнивание по ширине).

Отчет должен содержать следующие структурные разделы:

1. Титульный лист.
2. Цель работы.
3. Основная часть (отчет по модулям): пошаговое описание выполнения заданий с приведением конфигураций и скриншотов из SIEM.
4. Заключение: краткие выводы о проделанной работе, приобретенных навыках и роли SIEM-систем в структуре центров кибербезопасности.
